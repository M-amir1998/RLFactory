# First GPU experiments

This guide takes a prepared RLFactory run to a GPU host you control. Nothing here creates or pays
for cloud resources; you bring an SSH-reachable machine with an NVIDIA GPU.

## 1. Choose and pin a model

Small open models verified on 2026-11-14 (re-check the model card before every run):

| Model | Licence | Gated | Notes |
|---|---|---|---|
| `Qwen/Qwen3-0.6B` | Apache-2.0 | no | default in the example configs |
| `Qwen/Qwen3-1.7B` | Apache-2.0 | no | |
| `Qwen/Qwen2.5-0.5B-Instruct` / `-1.5B-Instruct` | Apache-2.0 | no | |
| `HuggingFaceTB/SmolLM3-3B` | Apache-2.0 | no | |
| `meta-llama/Llama-3.2-1B-Instruct` | Llama 3.2 licence | yes | needs an accepted licence and HF token on the host |
| `google/gemma-3-1b-it` | Gemma terms | yes | |

The example configs set `revision: null` on purpose. Pin a commit SHA (the `sha` field of
`https://huggingface.co/api/models/<model-id>`) in the training config before a remote run; the
remote preflight refuses unpinned models. Keep `trust_remote_code: false`.

## 2. Build training data from real rollouts

Training data generated by the mock policy is only useful for testing the pipeline. For a real
study, roll out the base model itself. Start an OpenAI-compatible server on the GPU host and tunnel
it to the laptop:

```bash
# on the GPU host, from an RLFactory checkout inside its vLLM environment
scripts/gpu/serve_vllm.sh Qwen/Qwen3-0.6B <sha>
# on the laptop
ssh -N -L 8000:127.0.0.1:8000 my-gpu-box
```

The script binds the server to the host's loopback interface (`--host 127.0.0.1`), so only the
tunnel reaches it. If you serve on a reachable interface instead, also start vLLM with
`--api-key "$VLLM_API_KEY"` and add `api_key_env: VLLM_API_KEY` to the policy in your copy of the
rollout config: only the variable name is stored, and the policy refuses to start when the variable
is unset.

Then run rollouts against it and build datasets:

```bash
uv run rlfactory rollout run configs/rollouts/vllm-train-mixed.yaml --run-id qwen3-base-rollouts
# copy configs/datasets/sft-from-mock.yaml, set name and source_run: qwen3-base-rollouts
uv run rlfactory dataset build-sft  <your-dataset-config>.yaml
uv run rlfactory dataset build-dpo  <your-dataset-config>.yaml
uv run rlfactory dataset build-grpo <your-dataset-config>.yaml
uv run rlfactory dataset validate results/datasets/<name>-sft
```

`configs/rollouts/vllm-train-mixed.yaml` uses the Docker sandbox for generated code; pull the image
first (`docker pull python:3.12-slim`) or switch it to `subprocess` knowingly. Point
`dataset_dir` in the training config at the dataset you built.

## 3. Prepare the run and estimate memory

```bash
uv run rlfactory train configs/training/trl-sft-qwen3-0.6b.yaml --dry-run
```

This writes `results/training/trl-sft-qwen3-0.6b/` (`run_config.json`, `launch.sh`, `data/`,
`prepared.json`) and prints a heuristic GPU-memory estimate when the model's shape is known (a
built-in shape or a `config.json` in the local Hugging Face cache). The estimate is a planning aid;
the smoke step below is the real check.

## 4. Describe the host

```bash
cp configs/remote/gpu-host.example.yaml configs/remote/gpu-host.yaml   # git-ignored
```

Set `host` to an alias from your `~/.ssh/config`, absolute `workspace` and `code_dir` paths, and the
setup commands for the training environment (`uv sync --extra trl --extra gpu`). The `activate`
command runs from `code_dir` before each remote command changes into its run directory, so the
example's `activate: source .venv/bin/activate` refers to the checkout's environment. Never put
tokens in this file; set `HF_TOKEN` on the host itself if a gated model needs it.

## 5. Check, launch, monitor, fetch

```bash
uv run rlfactory remote check configs/remote/gpu-host.yaml
uv run rlfactory remote launch results/training/trl-sft-qwen3-0.6b --host configs/remote/gpu-host.yaml --dry-run
uv run rlfactory remote launch results/training/trl-sft-qwen3-0.6b --host configs/remote/gpu-host.yaml
uv run rlfactory remote status results/training/trl-sft-qwen3-0.6b --host configs/remote/gpu-host.yaml
uv run rlfactory remote fetch  results/training/trl-sft-qwen3-0.6b --host configs/remote/gpu-host.yaml
```

Run these from the repository root (`remote launch` syncs `src`, `configs`, `scripts`,
`pyproject.toml`, `uv.lock`, `README.md` and `LICENSE` from the current directory). `launch` asks
for confirmation, runs the preflight, syncs code and the run directory, runs the setup commands,
executes a two-step smoke run and then starts `launch.sh` with `nohup`. `--skip-smoke`,
`--no-sync-code` and `--no-prepare-env` skip individual steps. `fetch` downloads status, metrics,
the training summary, the launcher log and the adapter's small JSON files; weights stay on the host.

## 6. Evaluate the checkpoint

Serve the base model with the trained adapter on the GPU host and evaluate through the tunnel:

```bash
# on the GPU host (loopback only, as above; vLLM's default maximum LoRA rank of 16 matches the
# example configs)
scripts/gpu/serve_vllm.sh Qwen/Qwen3-0.6B <sha> candidate=<workspace>/trl-sft-qwen3-0.6b/outputs/final
# on the laptop: evaluate the base model first (label: base, model: Qwen/Qwen3-0.6B, no baseline)
uv run rlfactory evaluate <base-eval-config>.yaml --run-id qwen3-base-eval
uv run rlfactory evaluate configs/evaluation/vllm-candidate.yaml --run-id qwen3-sft-eval
```

`configs/evaluation/vllm-candidate.yaml` gates the candidate against
`results/qwen3-base-eval/evaluation/base.json` and exits with code 2 when a gate fails.

## GRPO specifics

`configs/training/trl-grpo-qwen3-0.6b.yaml` uses TRL's colocated vLLM generation
(`use_vllm: true`, `vllm_mode: colocate`, `vllm_gpu_memory_utilization: 0.35`). For server mode,
run the TRL-compatible server on **separate GPUs**:

```bash
CUDA_VISIBLE_DEVICES=0 VLLM_SERVER_DEV_MODE=1 vllm serve Qwen/Qwen3-0.6B \
  --weight-transfer-config '{"backend": "nccl"}' --logprobs-mode processed_logprobs --max-logprobs -1
```

and set `vllm_mode: server` with `vllm_server_base_url`. GRPO reward functions execute RLFactory
verifiers on the GPU host, including the Python sandbox, so the host's training environment needs
RLFactory installed (it is, via `code_dir`). Multi-step tool-use tasks are excluded from GRPO data
in v0.1.

## verl and OpenRLHF

```bash
uv run rlfactory train configs/training/verl-grpo-qwen3-0.6b.yaml --dry-run
uv run rlfactory train configs/training/openrlhf-grpo-qwen3-0.6b.yaml --dry-run
```

Both write complete run directories, but the frameworks must be installed in their own
environments on the GPU host (verl 0.9.1 pins transformers 5.9.0 and Python < 3.13; OpenRLHF 0.11.2
needs Ray and its own vLLM). Before launching, dry-run the generated command there: append
`--cfg job` to verl's `python3 -m verl.trainer.main_ppo ...` to print the resolved Hydra config, and
run `python3 -m openrlhf.cli.train_ppo_ray --help` to confirm the dotted flags. The reward shims
import `rlfactory`, so RLFactory must be importable in those environments too.
